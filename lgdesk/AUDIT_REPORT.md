### 4. tests.gs's own authors already knew about this drift — for *some* suites

The "Contract-oriented helpers" block (`tests.gs:75-97`, `_safeCall`, `_assertContractOk`, `_assertContractFail`) contains an explicit, self-aware comment:

> "These keep newer tests running even when the implementation still throws or returns legacy raw IDs; the assertions decide whether the observed result satisfies the public contract."

This proves the divergence documented above (§3) was **known**, at least in part, at some point in `tests.gs`'s life. But the fix was only applied to the suites added later in the file — `testEdgeCaseContracts()` (`tests.gs:890-899`) and `testSecurityHardening()` (`tests.gs:1301-1310`), both of which wrap every risky call in `_safeCall(...)` and assert via `_assertContractOk`/`_assertContractFail` rather than raw `_assertOk`/`_assertFail`. The **older** suites (`testAuth`, `testSessions`, `testTasks`, `testProjects`, `testWorkLogs`, `testNotesTodoIdeas`, `testDashboard`, `testMigration`, `testPresence`) were **never retrofitted** to use these same defensive helpers, and it is exactly those older suites where §3's mismatches live. **NEEDS DECISION: none** — this is a diagnosis, not a product decision, but it is worth recording because it changes the correct inference: this is not random bit-rot, it is a file whose *maintenance* stopped partway through applying its own known fix.

### 5. A structural nuance worth flagging for later phases: the rebuild's `{ok:true,data}` envelope matches tests.gs's assumption more than the current reference does

`apps/api/src/common/interceptors/response.interceptor.ts:8` (`return next.handle().pipe(map(data => ({ ok: true, data })));`) wraps **every** successful NestJS response in a uniform `{ ok:true, data:<payload> }` envelope — this is exactly the uniform contract `tests.gs` assumes throughout (§3, rows 1–13). The actual current `reference/auth.gs` (and several sibling `.gs` files) has drifted away from that uniform contract for Tasks/Projects/Sessions/Progress-Updates specifically (bare-value-or-throw), while still using it faithfully for Functions CRUD, Leaves, Presence-set, Directory, Announcements, and Work-Duration. **This means when a later phase (A1+) compares a Next.js endpoint like "create task" against `reference/auth.gs`'s `createTask`, the correct comparison is against the bare-string-return behavior actually in the reference file today (`auth.gs:895`) — not against what `tests.gs` (or the Next.js envelope) would lead you to expect.** Flagging this explicitly so A1+ doesn't accidentally use the Next.js envelope shape, or `tests.gs`'s assumptions, as a stand-in for what the reference actually does. **[FUNCTIONAL] NEEDS DECISION: this is not a bug to fix in A0, but later phases should decide whether "the Next.js API always returns `{ok,data}`" is treated as a deliberate, acceptable normalization over the reference's inconsistent contract, or as a genuine parity gap** — CLAUDE.md's 22-rules list and file layout doc are silent on this specific point, and (per the standing ground rule) `LGDesk_Master_Reference.md` cannot be consulted to check — **cannot verify — LGDesk_Master_Reference.md not present in this repo.**

### Verdict

**Partial trust, with named caveats — do not treat `tests.gs` as a reliable oracle for exact return-shape/field-name contracts anywhere in the file, but its RBAC/business-rule *intent* (who is allowed to do what, and why) remains a reasonably faithful witness in most of the suites it actually contains.** Concretely, for A1–A9:

- **Do not rely on `tests.gs` at all** for exact API return shapes on: Sessions (`createSession`/`validateSession`), Tasks CRUD, Projects CRUD, Progress Updates, Work Log submission/retrieval, Notes/Todos/Ideas, and `getDeployerEmail`/migration preview. In every one of these, read the actual current `.gs` file directly (as this report's citations do) rather than inferring the contract from `tests.gs`'s assertions.
- **Treat `testProjects()` as evidence the reference itself has an inconsistency worth flagging on its own terms** (an unguarded `throw` where sibling functions return `{ok:false}}`), independent of whether the Next.js rebuild copies that inconsistency — that's a legitimate A1+ finding to make by reading `auth.gs:944` directly, not by trusting `tests.gs`'s expectation that it returns `{ok:false}` gracefully.
- **Full trust is reasonable** for: Directory, Functions/Sub-Functions CRUD (with the one self-assign caveat above), Work Duration's core clock flow, DB helpers, and the RBAC-scoping/security-hardening suites (which use the file's own newer, contract-aware assertion helpers and were spot-verified against current code).
- **Zero coverage, not wrong coverage**, for Intern work-log, Chat/Chat Spaces, Meet, Forms, Attachments, Due-Date-Requests, and Weekly Summary — `tests.gs` says nothing about these areas either way, so later phases should audit them purely from `reference/*.gs` + `app.js.html`/`index.html` with no test-file cross-check available.
- **Structural risk, not just data risk**: if any future phase's process literally involves *running* `tests.gs` (e.g., via `clasp run runAllTests`) against a live dev DB to "check current behavior," be aware it will very likely throw and halt inside `testProjects()` before completing the full suite — plan for that rather than being surprised by a truncated Logger output.

### 5. Task/Project/Function DELETE scoping — NEEDS DECISION: the rebuild replaced the reference's ownership/assignee model with a team-string-match model, in both directions (over- and under-permission)

This is the most significant finding in this phase. The task brief lists "task/project/function delete scoping rules" as one of the "already-approved deviations" to reconfirm intact — the code that exists does **not** match what the `.gs` reference actually implements, in ways that go both stricter and looser than the reference simultaneously. Since `LGDesk_Master_Reference.md` cannot be consulted, it is unconfirmable whether this replacement was itself the "already-approved deviation," or whether it is an unintentional drift from a *different*, narrower approved deviation. **NEEDS DECISION.**

**Tasks:**
- Reference `deleteTask` (`auth.gs:1024-1041`): non-admin allowed iff `isOwner` (`task.Assigner_ID === user.empId`, **any role**, no team check) **OR** (`_isManager(user.role)` **AND** `isAssignee`, i.e. personally in `Assignee_IDs` — **not** a team-field match).
- Rebuild `canDeleteTask` (`tasks.service.ts:315-320`): `isAdmin` → true; `isManager(caller.role) && caller.team && parseIds(task.assignedTeams).includes(caller.team)` → true; `caller.role === 'Team Member' && task.assignerId === caller.empId` → true; else false.
- **[FUNCTIONAL/SECURITY] Divergence, both directions:**
  - *Under-permission*: a Team Captain/Team Facilitator personally listed in a task's `Assignee_IDs` (the common case — most tasks are assigned to specific people, not whole teams) but whose own `team` string is not present in that task's `assignedTeams` field (also the common case, since `assignedTeams` is a separate, optional, rarely-populated field per `_resolveTeamsToIds`) is granted delete rights by the reference (`isManager && isAssignee`) but **denied** by the rebuild (no assignee-based branch at all for managers). A TC/TF who created a task (is `Assigner_ID`) but is not a Team Member is also denied in the rebuild's `caller.role === 'Team Member'`-only owner branch, though the reference's `isOwner` check has no role restriction.
  - *Over-permission*: a manager whose team string happens to match a task's `assignedTeams` field, but who is neither the task's assigner nor an assignee, is granted delete rights by the rebuild but would **not** qualify under the reference's `isManager && isAssignee` clause at all (reference has no team-field-based delete path for tasks whatsoever).

**Projects:**
- Reference `deleteProject` (`auth.gs:1043-1056`): `if (!_isManager(user.role)) throw` (managers/admins only, this part matches); then for non-admin managers, `proj.Assigner_ID !== user.empId && Owner_IDs.indexOf(user.empId) === -1 → throw` — i.e., **creator or permanent owner only, zero team-based check**.
- Rebuild `canDelete` (`projects.service.ts:217-221`): `isAdmin` → true; `isManager(caller.role) && caller.team && parseIds(p.assignedTeams).includes(caller.team)` → true; else false. **There is no ownerIds/assignerId check in the delete path at all** (contrast with `canModify`, `projects.service.ts:204-213`, which does check `ownerIds`/`assigneeIds`/assignerId in addition to team).
- **[SECURITY] Divergence, both directions:** a TC/TF who is the project's creator or a permanent owner (`Owner_IDs`, "permanent owner = creator, never overwritten" per `createProject`, `auth.gs:948`) cannot delete their own project in the rebuild unless their team string also happens to match `assignedTeams` — a real, likely-common regression given `Owner_IDs`/`Assigner_ID` is the reference's *only* non-admin delete gate for projects. Conversely, any manager whose team matches `assignedTeams` — with zero ownership stake — can delete a project in the rebuild that the reference would have rejected outright (no team-based path exists in `deleteProject` at all).

**Functions:**
- Reference `deleteFunction` (`auth.gs:1115-1137`): `if (!_isManager(user.role)) throw` — **and nothing else**. Any manager (TC, TF, Admin, SA) can delete **any** function org-wide, with no ownership or team check whatsoever.
- Rebuild `canDelete` (`functions.service.ts:211-217`): `isAdmin` → true; `isManager(caller.role) && caller.team && parseIds(f.assignedTeams).includes(caller.team)` → true; else false.
- **[SECURITY] Divergence — rebuild is materially *more restrictive* than the reference here**, not less: reference intentionally grants blanket cross-team delete power to any manager (matching its "Only managers can delete functions" comment, no further scoping); the rebuild scopes it to team-matching managers only. This is the inverse-severity case of the Tasks/Projects findings above — worth confirming deliberately, since a narrower policy might be the actually-desired one, but as written it is not what `auth.gs` implements.
- Also note: reference's `updateFunction` (`auth.gs:1098-1106`) gives **any** manager unrestricted update rights (`if (!_isManager(user.role)) { ...isAssignee/isCreator check... }` — the check only runs for non-managers), whereas the rebuild's `canModify` (`functions.service.ts:203-209`) adds a `caller.team && assignedTeams.includes(caller.team)` requirement even for managers who are not the function's assigner/creator/assignee. Same directional divergence as delete.

**Cross-check against the rebuild's own LIST-view scoping** (not itself wrong, but shows the DELETE path is inconsistent even internally): `tasks.service.ts`'s `visibleToManager` (`:356-361`) and `managerScopeIds` (`:347-350`) grant *view* access via the caller's **subordinate tree** (`UsersService.getSubordinateIds`, BFS over `Manager_ID`, `users.service.ts:102-124`) — a materially different and broader mechanism than either the reference's flat `_getTeamEmpIds` (same `Team` string, `auth.gs:641-651`) or the DELETE path's `assignedTeams`-field match. This subordinate-tree widening for *view* access is the one gap `apps/web/src/lib/rbac.ts`'s own header comment already documents as intentional (per `lgdesk/CLAUDE.md`'s "RBAC" section: "the one documented gap (manager-scope via org-chart subordinates)") — that part is **confirmed intact and expected**. What is *not* documented anywhere available to this audit is why DELETE (and Function UPDATE) uses a third, different mechanism (`assignedTeams` field match) that matches neither the reference nor the rebuild's own LIST-view/UPDATE-for-tasks-and-projects logic.

**NEEDS DECISION:** Confirm whether the `assignedTeams`-field-match delete/function-update model (`tasks.service.ts:315-320`, `projects.service.ts:217-221`, `functions.service.ts:211-217`, `:203-209`) was a deliberate, approved simplification of the reference's ownership/assignee model (cannot verify — `LGDesk_Master_Reference.md` not present in this repo), or an unintentional drift that should be reconciled with `auth.gs`'s actual `isOwner`/`isAssignee`/unrestricted-manager rules. ### 8. db.gs / setupSheets.gs uniqueness & cascade semantics vs. `schema.prisma`

**8a. WorkLog one-row-per-day — schema is *stricter* than the reference, NEEDS DECISION.**
Reference `submitWorkLog` (`auth.gs:1216-1256`) unconditionally `dbInsert`s a new `Work_Log` row for `(Emp_ID, Date)` with **no duplicate check** — it does not look up an existing row for that employee/date before inserting. `updateWorkLogStatus`/`updateWorkLogComment` (`auth.gs:1259-1280`) both use `.find()` keyed on `Emp_ID`+`Date`, which only ever touches the *first* matching row, implicitly assuming (but not enforcing) a one-row-per-day invariant. That invariant is evidently violated in practice: `work-duration.gs:36-177`'s `analyseWorkLogDuplicates`/`_wlAnalyseSheet` exists specifically to scan `Work_Log` and `Intern_Work_Log` for duplicate `(Emp_ID, Date)` rows (cited in A0 §6). By contrast, `apps/api/prisma/schema.prisma:164-186` (`model WorkLog`) has `@@unique([empId, date])` (line 186) — a hard DB constraint that would make a second `submitWorkLog`-equivalent call for the same employee/day **fail outright** (Prisma `P2002`) rather than silently create a duplicate row the way the reference sheet does today. **NEEDS DECISION**: confirm this stricter DB-level constraint is an intentional data-quality improvement (plausible — it would prevent exactly the duplicate-row problem `analyseWorkLogDuplicates` was written to clean up) rather than a schema change made without registering the corresponding behavior change (e.g., does the work-log submission endpoint handle the resulting unique-constraint conflict gracefully as an "already logged today" user-facing message, or would it surface as a raw 500?) — the work-log submission service itself (`apps/api/src/work-log/*`) is outside this phase's assigned file list, so this is flagged for the phase that does cover it, not resolved here.

**8b. Task → Project/Function foreign keys rely on Prisma's implicit default `onDelete`, not an explicit annotation — NEEDS DECISION (schema-adjacent).**
`schema.prisma:94-96`:
```
project         Project?       @relation(fields: [projId], references: [projId])
function        WorkFunction?  @relation("FunctionTasks", fields: [functionId], references: [functionId])
subFunction     WorkFunction?  @relation("SubFunctionTasks", fields: [subFnId], references: [functionId], onDelete: SetNull)
```
Only the `subFunction` relation has an explicit `onDelete: SetNull`; `project` and `function` have none, relying on Prisma's implicit default action for optional scalar foreign keys. No `apps/api/prisma/migrations/` directory exists in this repo (confirmed via `find`), meaning the schema is applied via `db push` rather than versioned migrations — there is no SQL artifact in-repo to directly confirm which referential action Postgres actually has for the `project`/`function` foreign keys today. This matters because the reference's own `deleteProject` (`auth.gs:1043-1056`) does **not** touch `Tasks`/`Functions` at all when a project is deleted — in the Sheets model this simply leaves `Task.Proj_ID` pointing at a now-nonexistent project row (a silent dangling reference, tolerated because Sheets have no FK enforcement). If Postgres's actual constraint here is anything other than `SetNull` (e.g. a default `Restrict`/`NoAction`), `ProjectsService.deleteProject` (`projects.service.ts:158-166`) would throw a raw foreign-key-violation error on any project that still has tasks/functions attached, which the reference never does (it always "succeeds," just leaves orphaned Proj_IDs behind). **NEEDS DECISION**: confirm the actual deployed constraint (e.g. via `prisma migrate diff` against the live Neon DB, or by adding an explicit `onDelete: SetNull` to remove the ambiguity) — this audit did not run that check since it would touch schema/DB state, which is out of scope for a read-only audit phase.

**8c. ProgressUpdate cascades on Task delete — reference leaves orphans, rebuild deletes them.**
`schema.prisma:438`: `task Task @relation(fields: [taskId], references: [taskId], onDelete: Cascade)` — confirmed by the rebuild's own comment at the call site, `tasks.service.ts:258`: `await this.prisma.task.delete({ where: { taskId } }); // ProgressUpdates cascade via FK`. Reference `deleteTask` (`auth.gs:1024-1041`) only ever calls `dbDeleteRow('Tasks', 'Task_ID', taskId)` — it never touches `Progress_Updates`, so in the Sheets model, progress-update rows referencing a deleted task are left behind permanently (orphaned, but harmless since nothing reads them without a valid Task_ID join). **[FUNCTIONAL], low severity, arguably a correctness improvement** — flagging per the ground rule that any cascade-behavior difference from the Sheets model should be surfaced, not because this specific instance looks harmful (it prevents orphan rows rather than causing data loss of anything a user could still reach).

**8d. `TEAM_HIERARCHY` (Team → Sub_Department rollup) — not represented in `constants.ts`.**
`setupSheets.gs:67-88` defines an explicit `TEAM_HIERARCHY` map (8 top-level divisions → their `Sub_Department` values) used by `_resolveTeamsToIds` (`auth.gs:236-239`) to let a Team Captain/Team Facilitator's "assign to team" action match employees by **either** an exact `Team` string match **or** membership in one of that division's listed sub-departments. `apps/api/src/common/constants.ts` has no equivalent structure — every team-scoping check found in this phase (`caller.team && ...includes(caller.team)`, throughout `tasks.service.ts`/`projects.service.ts`/`functions.service.ts`) is a flat string match against a single `team` field, with no sub-department rollup. **[FUNCTIONAL]** — this means any employee whose `Sub_Department` (not `Team`) is what identifies them with a division (per `TEAM_HIERARCHY`) would not be matched by the rebuild's flat team-string checks the way `_resolveTeamsToIds` would match them in the reference. Whether the rebuild's `User.team`/`User.subDepartment` fields (referenced in `users.service.ts`) already fold this rollup in at write-time (so a flat match suffices) versus needing it at read-time (every RBAC check) was not resolved in this phase — flagged here since `setupSheets.gs`'s schema explicitly encodes a hierarchy that no rebuild file in this phase's scope reproduces structurally.

### 2. Same formula with realistic (non-zero-second) timestamps — rounding-function divergence, not caught by the clean example

Both break-duration rounding and gross-elapsed-time rounding use **different functions** between the two systems:

| Quantity | Reference | Rebuild | Divergence |
|---|---|---|---|
| Per-break minutes | `Math.round(_wdMinsBetween(...))` (`work-duration.gs:189` `wdEndBreak`; also `:99` inside `wdClockOut`'s auto-close-open-break path) | `Math.ceil((now − breakStart)/60000)` (`work-duration.service.ts:63` `endBreak`) | **[FUNCTIONAL]** `Math.round` vs `Math.ceil` — identical only when the break duration lands exactly on a whole minute (as in §1's example). | Gross elapsed time (clock-in→clock-out) | Kept as a raw float minutes value (`_wdMinsBetween`, no rounding) until the **single, final** `Math.round(totalMins − totalBreak)` (`work-duration.gs:129-130`) | `grossMinutes = Math.floor((clockOut − clockIn)/60000)` (`work-duration.service.ts:86`) — floored **before** subtracting break, with no further rounding of the final integer difference | **[FUNCTIONAL]** `Math.round` (once, on the whole session) vs `Math.floor` (on gross alone). ### 3. Break-total "source of truth" at clock-out time differs from the shared `getStatus` reconciliation logic

- By contrast, **both systems' "status" endpoints agree** on a `Math.max(sum-of-breaks, stored-field)` reconciliation: reference `wdGetStatus` (`work-duration.gs:270-276`, explicit comment "ensures a manual override via wdEditBreak is reflected") and rebuild `getStatus()` (`work-duration.service.ts:99-100`) both compute `Math.max(calculatedBreak/sumBreaks, storedBreak/s.totalBreakMins)`.

### 6. `wdEditTime`/`editTime` and the custom clock-out picker — timezone-interpretation bug in the rebuild (real-world HIGH severity)

The reference's entire Work_Duration system is timezone-consistent by construction: every timestamp is written and read as a **plain IST wall-clock string**, with no UTC step anywhere. `_nowTs()`/`_todayStr()` (`auth.gs:251-252`) format using `Session.getScriptTimeZone()` (Asia/Kolkata), and `wdEditTime`'s manual-edit path builds new Clock_In/Clock_Out values by direct string concatenation of the session's date plus the user-typed `HH:MM` — **no timezone math at all** (`work-duration.gs:304-320`, e.g. `newClockIn = datePart + 'T' + sHH + ':' + sMM + ':00'`), consistent with the same IST-wall-clock model used everywhere else in the file.

The rebuild stores `clockIn`/`clockOut` as Postgres `DateTime` (`schema.prisma:217-218`, UTC-based JS `Date` objects under the hood) — correct and timezone-agnostic for the plain "Clock In now"/"Clock Out now" flows, since both just stamp `new Date()` (a real, universal instant; unaffected by any of the below). But the **manual-edit paths introduce a genuine offset bug**:
- `applyTime()` (`work-duration.service.ts:263-271`), used by both `editTime()` (`:108-133`) and `clockOut()`'s `customTime` handling (`:79-85`), calls `d.setUTCHours(h, m, 0, 0)` — it interprets the user-supplied `HH:MM` as **UTC** hours, not IST.
- `clock-widget.tsx` prefills the "Edit today's times" modal's Start/End fields via `new Date(session.clockIn).toISOString().slice(11, 16)` (`apps/web/src/components/modules/work-duration/clock-widget.tsx:127-129`, repeated at `:148-150` for the COMPLETED/AUTO_CLOSED state) — this slices the **UTC** clock digits, so a real 09:00 AM IST clock-in (`03:30` UTC) displays to the user as **"03:30"**, not "09:00".
- `change-clock-out-modal.tsx`'s custom clock-out time picker defaults its hour/minute fields from the **browser's local clock** (`new Date().getHours()`/`.getMinutes()`, `apps/web/src/components/modules/work-duration/change-clock-out-modal.tsx:47-51`) — for an India-based user this is IST — then submits that value as `customTime` (`:61,69`) straight to the server, which reinterprets it as UTC via `applyTime`.

**Net effect**: any time confirmed through "Change clock-out time" or "Edit today's times" — both real, primary, user-facing features present in both systems — is silently shifted by IST's UTC+5:30 offset from what the user saw/intended, corrupting the persisted instant (and therefore `Net_Work_Mins`/OT) by ~5.5 hours whenever these two edit paths are exercised. This has no counterpart bug in the reference, which never crosses a UTC boundary anywhere in this file. **[FUNCTIONAL], high real-world severity** given these are everyday correction features, not rare admin tools, and the corruption directly affects payroll-adjacent OT data. Not marked NEEDS DECISION (it's a correctness bug, not a policy question) — flagging prominently for a fix.
