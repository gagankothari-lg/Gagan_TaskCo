### 5. Task/Project/Function DELETE scoping — NEEDS DECISION: the rebuild replaced the reference's ownership/assignee model with a team-string-match model, in both directions (over- and under-permission)

This is the most significant finding in this phase. The task brief lists "task/project/function delete scoping rules" as one of the "already-approved deviations" to reconfirm intact — the code that exists does **not** match what the `.gs` reference actually implements, in ways that go both stricter and looser than the reference simultaneously. Since `LGDesk_Master_Reference.md` cannot be consulted, it is unconfirmable whether this replacement was itself the "already-approved deviation," or whether it is an unintentional drift from a *different*, narrower approved deviation. **NEEDS DECISION.**

**Tasks:**
- Reference `deleteTask` (`auth.gs:1024-1041`): non-admin allowed iff `isOwner` (`task.Assigner_ID === user.empId`, **any role**, no team check) **OR** (`_isManager(user.role)` **AND** `isAssignee`, i.e. personally in `Assignee_IDs` — **not** a team-field match).
- Rebuild `canDeleteTask` (`tasks.service.ts:315-320`): `isAdmin` → true; `isManager(caller.role) && caller.team && parseIds(task.assignedTeams).includes(caller.team)` → true; `caller.role === 'Team Member' && task.assignerId === caller.empId` → true; else false.
- **[FUNCTIONAL/SECURITY] Divergence, both directions:**
  - *Under-permission*: a Team Captain/Team Facilitator personally listed in a task's `Assignee_IDs` (the common case — most tasks are assigned to specific people, not whole teams) but whose own `team` string is not present in that task's `assignedTeams` field (also the common case, since `assignedTeams` is a separate, optional, rarely-populated field per `_resolveTeamsToIds`) is granted delete rights by the reference (`isManager && isAssignee`) but **denied** by the rebuild (no assignee-based branch at all for managers). A TC/TF who created a task (is `Assigner_ID`) but is not a Team Member is also denied in the rebuild's `caller.role === 'Team Member'`-only owner branch, though the reference's `isOwner` check has no role restriction.
  - *Over-permission*: a manager whose team string happens to match a task's `assignedTeams` field, but who is neither the task's assigner nor an assignee, is granted delete rights by the rebuild but would **not** qualify under the reference's `isManager && isAssignee` clause at all (reference has no team-field-based delete path for tasks whatsoever).

**Projects:**
- Reference `deleteProject` (`auth.gs:1043-1056`): `if (!_isManager(user.role)) throw` (managers/admins only, this part matches); then for non-admin managers, `proj.Assigner_ID !== user.empId && Owner_IDs.indexOf(user.empId) === -1 → throw` — i.e., **creator or permanent owner only, zero team-based check**.
- Rebuild `canDelete` (`projects.service.ts:217-221`): `isAdmin` → true; `isManager(caller.role) && caller.team && parseIds(p.assignedTeams).includes(caller.team)` → true; else false. **There is no ownerIds/assignerId check in the delete path at all** (contrast with `canModify`, `projects.service.ts:204-213`, which does check `ownerIds`/`assigneeIds`/assignerId in addition to team).
- **[SECURITY] Divergence, both directions:** a TC/TF who is the project's creator or a permanent owner (`Owner_IDs`, "permanent owner = creator, never overwritten" per `createProject`, `auth.gs:948`) cannot delete their own project in the rebuild unless their team string also happens to match `assignedTeams` — a real, likely-common regression given `Owner_IDs`/`Assigner_ID` is the reference's *only* non-admin delete gate for projects. Conversely, any manager whose team matches `assignedTeams` — with zero ownership stake — can delete a project in the rebuild that the reference would have rejected outright (no team-based path exists in `deleteProject` at all).

**Functions:**
- Reference `deleteFunction` (`auth.gs:1115-1137`): `if (!_isManager(user.role)) throw` — **and nothing else**. Any manager (TC, TF, Admin, SA) can delete **any** function org-wide, with no ownership or team check whatsoever.

- **[SECURITY] Divergence — rebuild is materially *more restrictive* than the reference here**, not less: reference intentionally grants blanket cross-team delete power to any manager (matching its "Only managers can delete functions" comment, no further scoping); the rebuild scopes it to team-matching managers only. This is the inverse-severity case of the Tasks/Projects findings above — worth confirming deliberately, since a narrower policy might be the actually-desired one, but as written it is not what `auth.gs` implements.
- Also note: reference's `updateFunction` (`auth.gs:1098-1106`) gives **any** manager unrestricted update rights (`if (!_isManager(user.role)) { ...isAssignee/isCreator check... }` — the check only runs for non-managers), whereas the rebuild's `canModify` (`functions.service.ts:203-209`) adds a `caller.team && assignedTeams.includes(caller.team)` requirement even for managers who are not the function's assigner/creator/assignee. Same directional divergence as delete.

**Cross-check against the rebuild's own LIST-view scoping** (not itself wrong, but shows the DELETE path is inconsistent even internally): `tasks.service.ts`'s `visibleToManager` (`:356-361`) and `managerScopeIds` (`:347-350`) grant *view* access via the caller's **subordinate tree** (`UsersService.getSubordinateIds`, BFS over `Manager_ID`, `users.service.ts:102-124`) — a materially different and broader mechanism than either the reference's flat `_getTeamEmpIds` (same `Team` string, `auth.gs:641-651`) or the DELETE path's `assignedTeams`-field match. ### 8. db.gs / setupSheets.gs uniqueness & cascade semantics vs. `schema.prisma`

**8a. WorkLog one-row-per-day — schema is *stricter* than the reference, NEEDS DECISION.**
Reference `submitWorkLog` (`auth.gs:1216-1256`) unconditionally `dbInsert`s a new `Work_Log` row for `(Emp_ID, Date)` with **no duplicate check** — it does not look up an existing row for that employee/date before inserting. `updateWorkLogStatus`/`updateWorkLogComment` (`auth.gs:1259-1280`) both use `.find()` keyed on `Emp_ID`+`Date`, which only ever touches the *first* matching row, implicitly assuming (but not enforcing) a one-row-per-day invariant. That invariant is evidently violated in practice: `work-duration.gs:36-177`'s `analyseWorkLogDuplicates`/`_wlAnalyseSheet` exists specifically to scan `Work_Log` and `Intern_Work_Log` for duplicate `(Emp_ID, Date)` rows (cited in A0 §6). By contrast, `apps/api/prisma/schema.prisma:164-186` (`model WorkLog`) has `@@unique([empId, date])` (line 186) — a hard DB constraint that would make a second `submitWorkLog`-equivalent call for the same employee/day **fail outright** (Prisma `P2002`) rather than silently create a duplicate row the way the reference sheet does today. **NEEDS DECISION**: confirm this stricter DB-level constraint is an intentional data-quality improvement (plausible — it would prevent exactly the duplicate-row problem `analyseWorkLogDuplicates` was written to clean up) rather than a schema change made without registering the corresponding behavior change (e.g., does the work-log submission endpoint handle the resulting unique-constraint conflict gracefully as an "already logged today" user-facing message, or would it surface as a raw 500?) — the work-log submission service itself (`apps/api/src/work-log/*`) is outside this phase's assigned file list, so this is flagged for the phase that does cover it, not resolved here.

**8b. Task → Project/Function foreign keys rely on Prisma's implicit default `onDelete`, not an explicit annotation — NEEDS DECISION (schema-adjacent).**
`schema.prisma:94-96`:
```
project         Project?       @relation(fields: [projId], references: [projId])
function        WorkFunction?  @relation("FunctionTasks", fields: [functionId], references: [functionId])
subFunction     WorkFunction?  @relation("SubFunctionTasks", fields: [subFnId], references: [functionId], onDelete: SetNull)
```
Only the `subFunction` relation has an explicit `onDelete: SetNull`; `project` and `function` have none, relying on Prisma's implicit default action for optional scalar foreign keys. No `apps/api/prisma/migrations/` directory exists in this repo (confirmed via `find`), meaning the schema is applied via `db push` rather than versioned migrations — there is no SQL artifact in-repo to directly confirm which referential action Postgres actually has for the `project`/`function` foreign keys today. This matters because the reference's own `deleteProject` (`auth.gs:1043-1056`) does **not** touch `Tasks`/`Functions` at all when a project is deleted — in the Sheets model this simply leaves `Task.Proj_ID` pointing at a now-nonexistent project row (a silent dangling reference, tolerated because Sheets have no FK enforcement). If Postgres's actual constraint here is anything other than `SetNull` (e.g. a default `Restrict`/`NoAction`), `ProjectsService.deleteProject` (`projects.service.ts:158-166`) would throw a raw foreign-key-violation error on any project that still has tasks/functions attached, which the reference never does (it always "succeeds," just leaves orphaned Proj_IDs behind). **NEEDS DECISION**: confirm the actual deployed constraint (e.g. via `prisma migrate diff` against the live Neon DB, or by adding an explicit `onDelete: SetNull` to remove the ambiguity) — this audit did not run that check since it would touch schema/DB state, which is out of scope for a read-only audit phase.

**8c. ProgressUpdate cascades on Task delete — reference leaves orphans, rebuild deletes them.**
`schema.prisma:438`: `task Task @relation(fields: [taskId], references: [taskId], onDelete: Cascade)` — confirmed by the rebuild's own comment at the call site, `tasks.service.ts:258`: `await this.prisma.task.delete({ where: { taskId } }); // ProgressUpdates cascade via FK`. Reference `deleteTask` (`auth.gs:1024-1041`) only ever calls `dbDeleteRow('Tasks', 'Task_ID', taskId)` — it never touches `Progress_Updates`, so in the Sheets model, progress-update rows referencing a deleted task are left behind permanently (orphaned, but harmless since nothing reads them without a valid Task_ID join). **[FUNCTIONAL], low severity, arguably a correctness improvement** — flagging per the ground rule that any cascade-behavior difference from the Sheets model should be surfaced, not because this specific instance looks harmful (it prevents orphan rows rather than causing data loss of anything a user could still reach).

**8d. `TEAM_HIERARCHY` (Team → Sub_Department rollup) — not represented in `constants.ts`.**
`setupSheets.gs:67-88` defines an explicit `TEAM_HIERARCHY` map (8 top-level divisions → their `Sub_Department` values) used by `_resolveTeamsToIds` (`auth.gs:236-239`) to let a Team Captain/Team Facilitator's "assign to team" action match employees by **either** an exact `Team` string match **or** membership in one of that division's listed sub-departments. `apps/api/src/common/constants.ts` has no equivalent structure — every team-scoping check found in this phase (`caller.team && ...includes(caller.team)`, throughout `tasks.service.ts`/`projects.service.ts`/`functions.service.ts`) is a flat string match against a single `team` field, with no sub-department rollup. **[FUNCTIONAL]** — this means any employee whose `Sub_Department` (not `Team`) is what identifies them with a division (per `TEAM_HIERARCHY`) would not be matched by the rebuild's flat team-string checks the way `_resolveTeamsToIds` would match them in the reference. Whether the rebuild's `User.team`/`User.subDepartment` fields (referenced in `users.service.ts`) already fold this rollup in at write-time (so a flat match suffices) versus needing it at read-time (every RBAC check) was not resolved in this phase — flagged here since `setupSheets.gs`'s schema explicitly encodes a hierarchy that no rebuild file in this phase's scope reproduces structurally.

### 2. Same formula with realistic (non-zero-second) timestamps — rounding-function divergence, not caught by the clean example

Both break-duration rounding and gross-elapsed-time rounding use **different functions** between the two systems:

| Quantity | Reference | Rebuild | Divergence |
|---|---|---|---|
| Per-break minutes | `Math.round(_wdMinsBetween(...))` (`work-duration.gs:189` `wdEndBreak`; also `:99` inside `wdClockOut`'s auto-close-open-break path) | `Math.ceil((now − breakStart)/60000)` (`work-duration.service.ts:63` `endBreak`) | **[FUNCTIONAL]** `Math.round` vs `Math.ceil` — identical only when the break duration lands exactly on a whole minute (as in §1's example). A break lasting e.g. 30 min 10 sec (30.167 min): reference rounds to **30**, rebuild rounds up to **31** — the rebuild always rounds break time *up*, silently reducing every employee's credited net-work time by up to ~1 minute per break relative to the reference. |
| Gross elapsed time (clock-in→clock-out) | Kept as a raw float minutes value (`_wdMinsBetween`, no rounding) until the **single, final** `Math.round(totalMins − totalBreak)` (`work-duration.gs:129-130`) | `grossMinutes = Math.floor((clockOut − clockIn)/60000)` (`work-duration.service.ts:86`) — floored **before** subtracting break, with no further rounding of the final integer difference | **[FUNCTIONAL]** `Math.round` (once, on the whole session) vs `Math.floor` (on gross alone). Example: clock-in 09:00:00, clock-out 18:00:40 (540.667 raw minutes): reference → `Math.round(540.667 − 45)` = **496**; rebuild → `Math.floor(540.667)` = **540**, `540 − 45` = **495** — a 1-minute discrepancy purely from this step, before even considering the break-rounding difference above. Both differences compound (always in the same direction — rebuild under-counts relative to reference) whenever any clock action lands on a non-zero second, which is virtually every real server timestamp. |

Net effect: the task's specified example matches because it was constructed on exact minute boundaries; **any real-world session (server timestamps always carry seconds) will generally produce a slightly different Net_Work_Mins between the two systems**, always in the direction of the rebuild reporting equal-or-fewer net minutes than the reference would for the identical clock actions. Severity: **[FUNCTIONAL]**, low-magnitude per session (≤ a few minutes) but systematic and OT/payroll-adjacent.

### 3. Break-total "source of truth" at clock-out time differs from the shared `getStatus` reconciliation logic

- Reference `wdClockOut` **always re-sums `Work_Breaks` rows** for the session (`totalBreak = dbGetAll(_WDB_SHEET).filter(...).reduce(...)`, `work-duration.gs:111-113`) — it does **not** trust the session's own `Total_Break_Mins` field at all for this specific calculation, even though that field is also being maintained incrementally elsewhere (`wdEndBreak`, `:201-203`).
- Rebuild `clockOut()` uses **only** the session's stored cumulative `s.totalBreakMins` field (`work-duration.service.ts:87`) — it never re-sums the child `WorkBreak` rows at clock-out time.
- By contrast, **both systems' "status" endpoints agree** on a `Math.max(sum-of-breaks, stored-field)` reconciliation: reference `wdGetStatus` (`work-duration.gs:270-276`, explicit comment "ensures a manual override via wdEditBreak is reflected") and rebuild `getStatus()` (`work-duration.service.ts:99-100`) both compute `Math.max(calculatedBreak/sumBreaks, storedBreak/s.totalBreakMins)`.
- **[FUNCTIONAL] Divergence, edge case**: if `wdEditBreak`/`editBreak` (self-service manual break-total override, `work-duration.gs:507-545` ↔ `work-duration.service.ts:135-150`) is used to set a value *higher* than the true sum of individual break records, and the employee then clocks out normally (no further breaks), the **reference's final `Net_Work_Mins` silently reverts to the raw breaks-table sum**, discarding the manual override — while the **rebuild's final `netMinutes` honors the manual override** (since it reads `s.totalBreakMins` directly, which `editBreak` had already set). This is a real behavioral difference for the "edit break total, then clock out" sequence, not just a cosmetic one, and would show up as a different final logged duration for the same sequence of user actions.

### 4. Clock-out silently wipes any existing session `Notes` in the reference; rebuild preserves them

`wdClockOut` (`work-duration.gs:132,139`): `var notes = reason ? ('Clock-out edit: ' + reason) : '';` then `Notes: notes` in the `dbUpdate` call — this **unconditionally overwrites** the session's entire `Notes` field on **every** clock-out, including a completely ordinary "Clock Out" click with no `customTime`/`reason` (in which case `Notes` is reset to an empty string, discarding e.g. an earlier same-day `wdEditTime` audit-trail entry, `:344-349`, which had appended to `Notes`). ### 5. Auto clock-out (midnight-UTC = 05:30 IST boundary) — boundary logic matches; stored precision differs (schema-adjacent)

The headline rule (CLAUDE.md #9, "fires at midnight-UTC, not an 18-hour elapsed cap") is **confirmed accurate on both sides**: reference `wdAutoClockOut` (`work-duration.gs:367-455`, closes sessions with `Clock_In` before `todayMidnightUTC = Date.UTC(y,m,d,0,0,0,0)`) and rebuild `autoClockOut()` (`work-duration.service.ts:210-229`, `date: { lt: today }` where `today = todayUtc()`) both use the same UTC-midnight calendar-day boundary, not an elapsed-hours cap. **One precision difference**: reference's auto-close path computes `Net_Work_Mins` as a **float, kept to 2 decimal places** (`netWorkMins = Math.max(0, (grossSecs − breakSecs)/60)`, then `parseFloat(netWorkMins.toFixed(2))`, `work-duration.gs:408-410,419`) — e.g. an auto-closed session could legitimately store `495.33`. The rebuild's `grossMinutes`/`netMinutes` columns are `Int` (`schema.prisma:220-221`), and `autoClockOut()` floors gross to a whole minute before subtracting (`work-duration.service.ts:222-223`) — it **cannot** represent the reference's fractional-minute precision for auto-closed sessions even in principle. **[FUNCTIONAL], schema-adjacent, low severity** — flagging per the stop-and-flag rule since matching the reference's fractional precision would require widening `grossMinutes`/`netMinutes` from `Int` to `Float`/`Decimal`, a schema change; not recommending it, just noting it as a real, citable representational gap. **NEEDS DECISION** only in the narrow sense of "should this precision difference ever matter for payroll reconciliation" — otherwise low priority.

### 6. `wdEditTime`/`editTime` and the custom clock-out picker — timezone-interpretation bug in the rebuild (real-world HIGH severity)

The reference's entire Work_Duration system is timezone-consistent by construction: every timestamp is written and read as a **plain IST wall-clock string**, with no UTC step anywhere. `_nowTs()`/`_todayStr()` (`auth.gs:251-252`) format using `Session.getScriptTimeZone()` (Asia/Kolkata), and `wdEditTime`'s manual-edit path builds new Clock_In/Clock_Out values by direct string concatenation of the session's date plus the user-typed `HH:MM` — **no timezone math at all** (`work-duration.gs:304-320`, e.g. `newClockIn = datePart + 'T' + sHH + ':' + sMM + ':00'`), consistent with the same IST-wall-clock model used everywhere else in the file.

The rebuild stores `clockIn`/`clockOut` as Postgres `DateTime` (`schema.prisma:217-218`, UTC-based JS `Date` objects under the hood) — correct and timezone-agnostic for the plain "Clock In now"/"Clock Out now" flows, since both just stamp `new Date()` (a real, universal instant; unaffected by any of the below). But the **manual-edit paths introduce a genuine offset bug**:
- `applyTime()` (`work-duration.service.ts:263-271`), used by both `editTime()` (`:108-133`) and `clockOut()`'s `customTime` handling (`:79-85`), calls `d.setUTCHours(h, m, 0, 0)` — it interprets the user-supplied `HH:MM` as **UTC** hours, not IST.
- `clock-widget.tsx` prefills the "Edit today's times" modal's Start/End fields via `new Date(session.clockIn).toISOString().slice(11, 16)` (`apps/web/src/components/modules/work-duration/clock-widget.tsx:127-129`, repeated at `:148-150` for the COMPLETED/AUTO_CLOSED state) — this slices the **UTC** clock digits, so a real 09:00 AM IST clock-in (`03:30` UTC) displays to the user as **"03:30"**, not "09:00".
- `change-clock-out-modal.tsx`'s custom clock-out time picker defaults its hour/minute fields from the **browser's local clock** (`new Date().getHours()`/`.getMinutes()`, `apps/web/src/components/modules/work-duration/change-clock-out-modal.tsx:47-51`) — for an India-based user this is IST — then submits that value as `customTime` (`:61,69`) straight to the server, which reinterprets it as UTC via `applyTime`.

**Net effect**: any time confirmed through "Change clock-out time" or "Edit today's times" — both real, primary, user-facing features present in both systems — is silently shifted by IST's UTC+5:30 offset from what the user saw/intended, corrupting the persisted instant (and therefore `Net_Work_Mins`/OT) by ~5.5 hours whenever these two edit paths are exercised. This has no counterpart bug in the reference, which never crosses a UTC boundary anywhere in this file. **[FUNCTIONAL], high real-world severity** given these are everyday correction features, not rare admin tools, and the corruption directly affects payroll-adjacent OT data. Not marked NEEDS DECISION (it's a correctness bug, not a policy question) — flagging prominently for a fix.

### 2. Storage mechanism — confirmed Drive-backed (not Sheet-cell, not Blob-only), with metadata in a Sheet acting as the app's DB

Read directly from the actual upload/list/delete functions, not assumed from the common GAS pattern:

- A single shared Drive folder is lazily created and cached in Script Properties: `_getAttachmentsFolder` (`attachments.gs:7-16`, `DriveApp.createFolder('TaskMgmt_Attachments')`, `ATTACHMENTS_FOLDER_ID` property).
- `uploadAttachment` (`:39-81`) decodes the incoming base64 payload into bytes, wraps it in a Blob, and calls `folder.createFile(blob)` — the literal binary file lives in Google Drive (`:44-48`) — then sets `DriveApp.Access.ANYONE_WITH_LINK` / `VIEW` sharing (`:50`) so `viewUrl`/`downloadUrl` (`uc?export=view|download&id=<fileId>`, `:53-54`) work unauthenticated in the browser.
- Only **metadata** (`Attachment_ID, Entity_Type, Entity_ID, File_Type, Drive_File_ID, File_Name, MIME_Type, File_Size, Uploaded_By, Uploaded_At, Is_Active`) is persisted in a dedicated `"Attachments"` sheet inside the main spreadsheet (`_ensureAttachmentsSheet`, `:19-33`; `dbInsert`, `:64-76`) — the sheet is this app's general-purpose "DB" mechanism (same `dbInsert`/`dbGetAll`/`dbUpdate` helpers used everywhere else in `reference/db.gs`), not a special attachment-only mechanism.
- Delete (`:132-148`) is a **soft delete**: `Is_Active` flips to `'FALSE'` in the metadata sheet (`:144`) and the Drive file is best-effort trashed, non-destructively, wrapped in its own `try/catch` so a Drive failure never blocks the metadata soft-delete (`:143`, `DriveApp.getFileById(...).setTrashed(true)`), matching `lgdesk/CLAUDE.md`'s Business Rule #17 ("Attachment soft-delete: isDeleted=true — file stays in Google Drive").
- Delete authorization: uploader-or-admin only (`:140-141`, `rec['Uploaded_By'] !== user.empId && !_isAdmin(user.role) → reject`).

**Conclusion: hybrid storage — binary bytes → Google Drive (`DriveApp`), structured metadata → the app's Sheet-backed "DB".** Not Sheet-cell-embedded binary, not a third-party Blob store. [FUNCTIONAL]

### 3. Credential dependency — independently confirmed NOT the same credential class as Chat/Forms (A7)

`reference/appsscript.json:9` declares a single, already-present native scope, `https://www.googleapis.com/auth/drive`, under `"webapp": {"executeAs": "USER_DEPLOYING", "access": "ANYONE"}` (`:4-5`) — i.e. Drive access in the reference is granted **once, automatically, at GAS deployment/authorization time**, running as the deploying user's own identity. `attachments.gs`'s own header comment even says this explicitly: *"Uses the existing 'drive' OAuth scope already declared in appsscript.json"* (`:4`). No separate OAuth client, no per-user consent flow, no token storage table.

By contrast, `reference/chatSpaces.gs` and `reference/forms.gs` (A7's scope) implement a **structurally different** credential mechanism: a self-registered GCP OAuth2 client (`KEEP_CLIENT_ID`/`SECRET`, reused across Chat/Forms/Google-Tasks) with a full authorization-code + refresh-token dance, storing **per-user** refresh tokens keyed by email (`chatSpaces.gs:3,19,51,111` — `chat_rt_{email}`; `forms.gs:3,9,51,93` — `forms_rt_{email}`), then calling `chat.googleapis.com`/`forms.googleapis.com` directly via `UrlFetchApp` with a bearer token (`chatSpaces.gs:464-468`, `forms.gs:116-120,156-157`). `forms.gs:4` even documents the extra setup burden explicitly: *"Setup: GCP → enable 'Google Forms API', add scopes to OAuth consent screen."* Neither `reference/appsscript.json`'s scope list (`spreadsheets`, `drive`, `userinfo.email`, `script.external_request`, `calendar`, `script.scriptapp`, `gmail.send`, `:8-16`) nor `attachments.gs` contains any Chat- or Forms-specific scope or reference to `KEEP_CLIENT_ID`.

**Independent conclusion: Attachments is NOT blocked on the same credential as Chat/Forms.** It needs a Drive-capable credential of the same *general family* the rebuild already has partial infrastructure for via Calendar sync (`GOOGLE_SERVICE_ACCOUNT_EMAIL`/`GOOGLE_PRIVATE_KEY`, per `lgdesk/CLAUDE.md`'s Google Integrations section) — i.e. one service-account key with a Drive scope added — whereas Chat/Forms need an entirely separate GCP OAuth2 **client** registration plus a new per-user refresh-token store that doesn't exist in either app today. `lgdesk/CLAUDE.md`'s "Google Integrations — blocked, do not implement" section currently lumps all four integrations under one blanket sentence ("blocked pending credentials that don't exist yet on Railway (no Google service account, no OAuth2 client)") without distinguishing these two materially different credential classes or their very different implementation cost. **NEEDS DECISION: worth product/eng explicitly deciding whether Attachments (lower lift — extends the existing service-account pattern) should be prioritized ahead of Chat/Forms (higher lift — new OAuth2 client + per-user consent + refresh-token storage), rather than treating all four as one bundled blocker.** [FUNCTIONAL]

### 5. GAP-002 re-verified directly against source: real in the reference (undefined server function), but the only call path into it is dead code — not a live data-loss bug

The function referenced by this client-side call is never defined anywhere in the actual GAS backend (`forms.gs` has no such function; nor does any other `.gs` file). If this code path executed, it would throw a GAS "submitFormResponse is not defined" runtime error, and the response would not be persisted.
- **However, tracing the only path that reaches this call proves it is dead code in practice, not a live bug**: the fill-page renderer, `_gfOpenFill(form)` (`app.js.html:14797-14825`), which builds the questions array `_gfSubmit` later reads from `form.Fields` (`:14842`), has **exactly one caller in the entire 819KB file** — `gfPreview()`'s `else` branch (`app.js.html:14684-14690`), which only runs when `!gfState.formId` (i.e., an unsaved draft in the form *builder*) and always constructs `fakeForm = { Form_ID: 'preview', ... }` (`:14688`). `_gfSubmit` itself explicitly guards against this: `if(!formId||formId==='preview'){toast('This is a preview — responses are not saved.','info');return;}` (`app.js.html:14839`) — an early return that fires *before* the `google.script.run...submitFormResponse(...)` call. **No other code path anywhere passes a real form to `_gfOpenFill`/`_gfSubmit`.** Every other place a real, saved form's fill/response link is presented to a user goes through the actual `Responder_URL` (`app.js.html:14445`, the "Fill" button on shared/notice-board forms — a real Google Forms `responderUri`, opened in a new tab), which submits directly to Google's own Forms servers, not to this app's backend at all.
- **Correct characterization**: GAP-002 is a genuine, confirmed dead reference to an undefined function (real defect in the reference source, as historically reported) — but it is **functionally inert**: it can never fire from any reachable user action, because its only entry point (`_gfOpenFill`) is only ever invoked with a synthetic `Form_ID:'preview'` object that `_gfSubmit` short-circuits before the undefined call. **Actual form-response persistence in the live production app is delegated entirely to Google's own Forms backend** (via the real `responderUri`) and is only ever *read back* — never written — by this app's own code, through `gfGetResponses` (`forms.gs:297-323`, `GET https://forms.googleapis.com/v1/forms/{formId}/responses`). [FUNCTIONAL], low real-world severity given the dead-code status, but the underlying "missing function" claim from prior audit history is confirmed accurate at the source level.
- **Rebuild side — the gap has not been "carried forward" because nothing exists yet to carry it into**: `apps/api/src` has no `forms/` module at all (confirmed §1), so there is no rebuild equivalent of `submitFormResponse` to check for the same defect. This is worth recording as forward-looking guidance rather than a current defect: **if/when Forms is eventually built in the rebuild, form-response submission should be implemented the way the reference's actually-working path does it — delegating to the real Google Forms API's native response collection (the public `responderUri`) and only reading responses back via the Forms API's `responses.list`, per `forms.gs:297-323`** — not by re-introducing a custom app-side "submit a response" endpoint (which would be a *new* build decision, since the original GAS app never had one that worked).
